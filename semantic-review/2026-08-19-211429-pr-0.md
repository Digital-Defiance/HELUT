# Unified Verilog-to-TensorLUT Mulein campaign with durable bounded receipts

The change joins the generated Future inventory, parameterized Verilog/Yosys bank, Float TensorLUT evaluator, host replay, and JSONL runner into one bounded P1030680 path. The benchmark supports W4, and the target ledger matches the published boundary exactly: shell 0 `B/beta/IV-III-VIII/AAAA`, identity Future 0, settings `0..<256`, 16 × 416 = 6,656 receipts, zero positives, and zero BREAK gates. All requested current-status surfaces preserve that narrow scope, distinguish the other 260 staged Futures, say cleartext rather than FHE, and retain Phase 51.13 as a historical pre-launch snapshot. The durable resume and eligibility contracts still have blocking gaps.

Watch for: **confirmed** loss of a previously recorded BREAK gate on resume; **confirmed** acceptance of semantically invalid “complete” rows; **confirmed** BREAK eligibility controlled by an unvalidated manifest label; **confirmed** task #14 remaining outside the current commit boundary; **likely** mixed runner semantics under one run ID; **confirmed** W4 evidence cited only from ignored build artifacts.

## High-level view

W4 is selected from equal semantic work, not synthesis size: all five widths report the same 256-receipt digest, and W4’s slowest measured repetition remains faster than W8’s fastest. The checked evaluator requires every active held receipt, verifies tags/seeds/configuration, proves consume/rearm, and the campaign host-replays every positive.

Resume remembers completed IDs but not the safety meaning of prior rows. A recorded BREAK gate is skipped and forgotten on restart, while any schema-valid row with a matching identity and expected ID can suppress a chunk without proving its shell/Future/range or complete accounting.

Exact identity/no-drop hits alone enter completion and scoring, but “identity” comes from a free-form manifest field that loading does not reconcile with the hypothesis. The run hash also omits an explicit campaign-semantics version, allowing future packer/replay changes to share an old identity.

Current-status prose is synchronized across `BREAK_P1030680.md`, `JournalPage.tsx`, `writeup.tex`/generated `writeup.md`, `MuleinBoardPage.tsx`, `directives/mulein-board.md`, and `Apps/Mulein/README.md`. The commit boundary is split instead: task #13 is staged, while task #14’s runner/evaluator/benchmark, bounded ledgers, and several final status updates are unstaged or untracked.

## Resume forgets a durably recorded BREAK gate

**Blocking, confirmed.** `P1030680MuleinJSONLLedger` loads `priorRecords`, including `breakGatePassed`, but campaign startup initializes `haltedForBreakGate = false` and consults only `completedChunkIDs` while skipping resumed chunks (`Sources/HELUTToolKit/P1030680MuleinCampaign.swift:151-152`, `:243-246`, `:742-760`). The halt is set only for a newly evaluated chunk (`:842-885`). After the intended first-run halt, an identical restart therefore skips the gated row, evaluates later chunks, and reaches `BOUNDED RUN COMPLETE` plus `NO BREAK CLAIM` (`:893-899`); prior positive counts also disappear from the summary.

Treat any prior gate as pending before scheduling evaluator work, preserve its candidate context, and aggregate prior/new counts. No resume should move beyond that row until the ledger/journal/report synchronization is explicitly resolved.

## Schema-valid rows can suppress unexecuted work

**High severity, confirmed.** Admission checks only schema/kind, full run-identity equality, and duplicate IDs (`P1030680MuleinCampaign.swift:217-232`), then the execution loop skips solely on ID (`:757-761`). It does not validate shell, Future, setting range, `attemptedReceipts`, digest/tick accounting, `positiveCount == candidates.count`, gate/candidate consistency, or reject unknown IDs. A row naming an expected chunk but carrying one setting or another Future is treated as complete even though the live writer requires `(upper-lower) × 26` duplicate-free receipts (`:812-830`, `:858-867`).

Build the exact planned chunk map first and validate every loaded row against it. Require the expected range/count, candidate and gate invariants, digest/tick presence, and no unknown IDs before adding to `completedChunkIDs`.

## A mutable family string decides BREAK eligibility

**High severity, confirmed.** The scoring branch requires `entry.family == "identity"`, an exact host replay, and no dropped edge; all other families remain physical hypotheses (`P1030680MuleinCampaign.swift:455-503`). Manifest loading checks counts and ordinals, while materialization proves serialized geometry/provenance but neither validates family against hypothesis nor recomputes `inventoryFingerprint` (`Sources/HELUTToolKit/MuleinFutureManifest.swift:253-288`). Relabeling a post-gap entry as identity changes the bound manifest SHA but is accepted in a new run, allowing shifted geometry into the identity gate.

Derive eligibility from validated edit/geometry semantics. The canonical loader should prove that identity entries are exact/no-edit Futures, post-gap entries carry the declared missing-recording edit and delta, and the recomputed fingerprint matches.

## Task #13 and #14 are not one commit yet

**Blocking, confirmed.** The index contains task #13’s mechanism/manifest work, while `MuleinFutureTensorLUTBench.swift`, `MuleinFutureTensorLUTEvaluator.swift`, `P1030680MuleinCampaign.swift`, and both `logs/p1030680-mulein-unified-smoke*.jsonl` remain untracked. The task #14 Makefile/CLI integration and final campaign status edits are also partly unstaged (`MM`/` M`). The working tree is coherent and builds, but a commit from the current index is not the combined path reviewed here; using only `git add -u` would add callers and claims while still omitting new source and receipts.

Stage the task #14 files explicitly if this is one combined commit. If task #13 is meant to land separately, exclude all task #14 status/caller updates and review task #14 as its own commit.

## Run identity can span incompatible runner behavior

**Medium severity, likely.** The identity binds manifest/netlist hashes, graph dimensions, device, plan, batch sizes, tick limit, and scope, but no runner protocol, packer ABI, replay policy, or build revision (`P1030680MuleinCampaign.swift:68-94`, `:549-580`). Unless every semantic change manually bumps generic `schemaVersion`, old rows can be skipped and new rows appended under one run ID.

Add a deliberate campaign-semantics version and bump it for changes to packing, receipt validation, replay, eligibility, or discriminator integration. A build revision can supplement, not replace, that compatibility boundary.

## W4 is measured, but the cited receipt is ephemeral

**Medium severity, confirmed.** The sweep launches fresh processes, rejects digest drift, and numerically sorts `median_receipts_per_s` (`Makefile:220-248`). Local logs show W4 at 275.560–276.310 receipts/s versus W8 at 273.672–274.586, with `fnv1a64-17435188996435da` for every width; the W4 graph hash/dimensions match all 16 campaign rows.

The cited selection and five logs live under `build/mulein`, while `.gitignore:11` excludes `/build/`. Preserve a small tracked receipt containing the command, artifact SHA-256, shared digest, per-width medians, and selection; the generated 134 MB netlists can remain ignored.

## Existing grades do not exercise durable resume failures

**Medium severity, confirmed.** No test references the private ledger or campaign runner. Future semantics and four-surface circuit parity are covered, but torn-tail/interior recovery, semantic row mismatch, unknown chunks, identity drift, all-skipped aggregation, and a pre-existing gate are not.

Extract package-visible ledger/plan validation and test those cases in temporary directories. The prior-gate test should prove that restart performs no evaluator work and appends nothing.
