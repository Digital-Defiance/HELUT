# Independent Rust E256 and Yosys reference lane

This adds a CPU-only Rust consumer for the frozen E256-v2/gen0 schema-3 KAT and a clear evaluator for the Yosys subset modeled by Swift. The E256 path binds profile identity, the receipt, exact bundle bytes/layout, all 1,024 state transitions, and reciprocal decrypt; the Yosys path independently checks three circuits under Swift’s host-tick DFF contract. `make rust-reference-check` passes, and the Rust implementation has no protected-tree writer. Watch for: **confirmed (medium)** root-level Make/README commands bypass toolchain selection; **confirmed (medium)** the checkout action is mutable; **confirmed (medium)** strict E256 rejection is only happy-path tested; **confirmed (medium)** accepted DFF variants exceed tested behavior.

**Verdict**: NEEDS_CHANGES

## High-level view

The E256 consumer is frozen rather than configurable. It recomputes canonical profile identity, requires the exact schema-3 session and 24-entry path/hash map, rejects extra entries and direct symlinks, validates all table relationships, recomputes 1,024 beats and eight traces, covers all four reserved-center branches, checks first/final checkpoints, and decrypts through a fresh reciprocal machine. The implementation is fail-closed, but tests do not lock in those rejection boundaries.

The Yosys evaluator matches `CleartextNetlistSim.swift` on cell ordering, LUT addressing/relaxation, post-update outputs, ignored clock values, and encoded enable/reset priority. Current fixtures cover combinational endianness and positive-high DFFE behavior; active-low and synchronous-reset variants remain unexercised.

Repository inputs are read-only, Cargo output is isolated, and CI checks `Fixtures`, `Hardware`, and `Generated` for tracked or untracked writes. Crate versions and transitives are exact/locked, but root-level Cargo commands do not activate the package-local 1.97.1 override, and `actions/checkout@v4` is not immutable.

README and CLI wording call this an internal parity consumer, explicitly leave the immutable external KAT outstanding, and do not close E256-050 or claim cryptographic security.

## Frozen E256 identity and 1,024-beat verification

`Reference/Rust/src/e256.rs` binds one immutable protocol point. Profile parsing rejects unknown/duplicate typed fields and validates E256/v2/gen0/schema-3 identity, component balance, tap partition/order, canonical hash, compatibility key, and receipt hash. Bundle parsing requires an exact root/tables/trace inventory of regular entries, and the manifest must equal the hard-coded 24-path hash map before artifact hashing.

The transition order matches Swift: derive the mask from current LFSR state, scramble with current offsets and mask-parity center mode, increment selected offsets, then apply the right-shift Galois step. All ten tables must be permutations; the plugboard must be involutory; each rotor pair is checked both ways; and the reflector must be fixed-point-free, involutory, and reserve `0 <-> 1`. The verifier cross-checks JSON/binary/line-hex streams, all eight semantic traces, all four `(center_mode, reserved_input)` branches, the detailed first beat, final state, and reciprocal decryption.

`Reference/Rust/tests/reference_parity.rs:10-25` only checks the valid bundle’s success report. Removing an exact-path comparison, symlink rejection, table invariant, trace-width/count check, branch gate, checkpoint, or reciprocal assertion could leave CI green. **Confirmed (medium):** add rejection tests for extra/missing/renamed paths, wrong hashes, duplicate/unknown schema fields, non-regular/symlink entries, invalid table relationships, short/altered traces, missing reserved branches, checkpoint drift, and reciprocal mismatch. Unit tests inside `e256.rs` can target semantic helpers without being stopped first by hard-coded artifact hashes.

## Swift-equivalent Yosys execution and unproven DFF variants

The evaluator mirrors Swift’s sorted cell compilation, MSB-string-to-LSB-address LUT conversion, combinational fixpoint, old-state DFF evaluation, post-update registered outputs, unresolved-control defaults, and SDFFE-versus-SDFFCE priority distinction. Counter and toy-ISA, however, contain only `$_DFFE_PP_`; the parser test at `Reference/Rust/src/yosys.rs:816-841` checks two `PN0P` descriptors without executing transitions. A wrong active-low enable, reset polarity/value, or reset-vs-enable priority implementation would pass every current test. **Confirmed (medium):** add parser vectors across DFF/DFFE/SDFF/SDFFE/SDFFCE encodings and synthetic transitions for enable levels, reset levels/values, and both priority orders, with Swift or reviewed shared expected outputs.

## Root commands do not activate the package toolchain

CI runs with `working-directory: Reference/Rust`, where rustup can discover the pinned `channel = "1.97.1"`. Make recipes at `Makefile:68-85` and README commands at `README.md:218-226` run from the repository root with `--manifest-path`; rustup searches the current directory and ancestors, not the manifest parent. Those paths therefore use the ambient toolchain, while `rust-version = "1.97"` only sets a minimum. The current machine happened to have Homebrew Rust 1.97.1, so validation passing does not establish portable selection. **Confirmed (medium):** run Cargo with the package as working directory or explicitly select/install 1.97.1 while retaining the external target directory.

## Isolated CI retains one mutable dependency

The workflow has read-only permissions, package-local execution, locked Cargo commands, separate verifier steps, and a final protected-tree cleanliness guard. `actions/checkout@v4` at `.github/workflows/rust-reference.yml:20` remains a retargetable major tag. **Confirmed (medium):** replace it with a reviewed full commit SHA and retain a comment naming the corresponding v4 release.
