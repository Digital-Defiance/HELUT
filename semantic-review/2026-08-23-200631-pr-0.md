# Schema-3 E256 center is functionally coherent but not closure-ready

The local change replaces the high-fixed-point center with a two-mode reciprocal center, binds it into E256-v2/gen0 fixture schema 3, and carries a 1,024-byte state trace through Swift, direct RTL, AXIS, AXI-Lite, and a read-only Rust consumer. The evidence is sufficient for implementation agreement and shows the original 29.42% equality symptom is absent on the bounded sample. It is not sufficient to mark E256-003 `CLOSED`: the alternative one-bit construction has no acceptance review, the mandatory closure record is absent, and active claim surfaces still describe old center/profile semantics.

Watch for: **confirmed, Critical** the center schedule is one NLFF-parity bit rather than an accepted reviewed masking construction; **confirmed, High** no E256-003 closure receipt records all mandatory fields and controls; **confirmed, High** the theorem, textbook, and public site retain pre-schema-3/gen5 claims; **confirmed, Medium** the equality control is a synthetic identity center labeled “historical,” with no separately identified known-good/null negative control.

**Verdict**: NEEDS_CHANGES

## High-level view

At position `i`, the outer plugboard/rotor path is a permutation `A_i`. Schema 3 uses a fixed-point-free base involution `F` with reserved pair `0↔1`; mode zero uses `F`, while mode one replaces only that transposition with two identity points. The byte map is therefore `A_i⁻¹ C_mode A_i(x)`, and parity of the captured pre-step mask chooses `C_mode` before that same mask advances offsets. Each position remains reciprocal with exactly zero or two fixed points; a balanced schedule and center input yield the target average equality rate of `1/256`.

The profile hash binds the center rule and timing, the atomic KAT hashes 24 artifacts and eight trace streams, generated plaintext forces all four `(mode, reserved input)` branches, direct RTL compares every pre/post state field, and Rust recomputes the machine rather than accepting Swift ciphertext as authority. AXIS and AXI-Lite add friendly table-ingress parity, not adversarial bus-protocol proof.

The remaining technical gate is construction acceptance, not coding. E256-003 asks for a reviewed per-position masking primitive; the shipped alternative derives one schedule bit from the same 64-bit LFSR/NLFF that drives stepping and changes only the reserved pair. Equality-rate regression establishes the fixed-point symptom, not why this schedule is cryptographically adequate or equivalent to the ledger’s reviewed 256-bit example.

The ledger still says `OPEN`, has no E256-003 receipt, and the theorem/textbook/site retain old un-reflector, `coupledCubic6`, and live-gen5 language. Those contradictions prevent the required claim/document review from being signed.

## Reserved-pair scheduling preserves reciprocity but lacks construction acceptance

Swift computes mode as parity of four pre-step enables and bypasses center inputs zero and one only in mode one (`Sources/HELUTCore/Enigma256.swift:157-165`). `processTraced` captures the mask once, applies the center, and advances state with that same value (`Sources/HELUTCore/Enigma256.swift:315-324`). RTL implements the same parity and reserved-input test (`Hardware/RTL/Enigma256/enigma_256_core.v:103-128`); exhaustive Swift maps and directed RTL vectors require zero/two fixed points and all four reserved branches (`Tests/HELUTTests/Enigma256Tests.swift:211-245`; `Hardware/Testbenches/Enigma256/enigma_256_center_tb.v:94-105`).

**Confirmed, Critical:** this differs from the closure row’s reviewed-mask construction. E256-003 asks for a reciprocal per-position mask such as `A_i^-1(A_i(x) XOR k_i)` with `k_i` from a reviewed counter-based 256-bit primitive (`directives/e256-audit.md:53-56`). Schema 3 selects between two maps using one parity bit (`Fixtures/enigma256_generation.json:3-4`), while its receipt explicitly claims only bounded functional evidence (`logs/e256-v2-gen0-center-equality.json:3-4,70`). No design note or reviewer field accepts that alternative or analyzes correlation with the shared stepping state. Functional parity cannot substitute for construction review.

## Branch-covering KAT and Rust establish implementation agreement

`Enigma256Bridge` fixes the KAT at 1,024 bytes, forces `(false,0)`, `(false,1)`, `(true,0)`, and `(true,1)`, and rejects incomplete branch coverage (`Sources/HELUTCore/Enigma256Bridge.swift:70-145,445-452`). The manifest binds schema, compatibility key, canonical profile bytes/hash, and 24 exact artifact hashes (`Fixtures/enigma256_golden/manifest.json:2-33`). Direct RTL checks LFSR, offsets, step mask, mode, center input/output, and ciphertext before and after every accepted beat (`Hardware/Testbenches/Enigma256/enigma_256_tb.v:43-51,83-91,119-168`).

Rust independently rebuilds the step mask, center, rotor path, and transition, then validates exact layout/hashes, all 1,024 traces, four reserved branches, first/final checkpoints, and reciprocal decrypt (`Reference/Rust/src/e256.rs:650-762,784-945`). Its integration test pins 1,024 bytes and 24 artifacts (`Reference/Rust/tests/reference_parity.rs:10-25`). This removes the same-authority weakness for implementation parity; it does not review the construction’s security.

This pass reproduced 43/43 Swift tests, `4083/1048576` equality, direct-RTL 1,024-beat PASS, directed-center PASS, AXIS 1,024-byte PASS, and Rust KAT PASS with branches `4/4` and reciprocal decrypt. The execution wrapper reports status 1 even for `true`, so explicit PASS markers were used. AXI-Lite reached `896/1024` without mismatch before the 30-minute cap; the checked-in testbench covers 1,024 (`Hardware/Testbenches/Enigma256/enigma_256_axi_tb.v:247-277`), but this pass did not independently reproduce its final marker.

## Equality evidence catches an extreme defect but leaves control provenance ambiguous

The test spans four deterministic keys, four nonces per key, and 65,536 zero bytes per stream. It observes 4,083 equal bytes against an independent-uniform expectation of 4,096 and gates at six nominal binomial standard deviations (`Tests/HELUTTests/Enigma256Tests.swift:280-350`; `logs/e256-v2-gen0-center-equality.json:23-47`). That satisfies the bounded-rate symptom check, and the spec correctly calls it a diagnostic rather than a security estimate (`Enigma256.md:232-235`).

**Confirmed, Medium:** the “historical” positive is synthetic. All-zero entropy causes the helper to make every entry a fixed point (`Tests/HELUTTests/Enigma256Tests.swift:283-293`; `Sources/HELUTCore/Enigma256.swift:538-559`), so it is an identity center with 100% equality, not the quarantined center that produced 29.42% (`logs/e256-v2-gen0-center-equality.json:48-57`). It is a useful extreme positive, but the closure template also requires a negative control (`directives/e256-audit.md:157-170`). Relabel it and add realistic v1 plus known-good/null controls, or record a reviewed equivalence rationale.

## Closure record and active claim surfaces are incomplete

**Confirmed, High:** the ledger marks E256-003 `OPEN`, and closure receipts jump from E256-001 to E256-004/E256-007/E256-010 (`directives/e256-audit.md:53-56,175-201`). The equality JSON has a command, profile, date, and tool versions, but omits the implementation diff, reviewed surfaces, reviewer, and explicit negative control required by `directives/e256-audit.md:157-170`. It also omits the later Rust evidence. A consolidated E256-003 receipt must narrow closure to the fixed-point-center defect; it must not imply confidentiality, protocol, or production-security closure.

**Confirmed, High:** active surfaces contradict schema 3. The theorem still defines an un-reflector with fixed points and `coupledCubic6` rollback (`directives/enigma256-theorem.md:15-34`). The public page first describes schema 3 correctly but later calls gen5/balanced-cubic6 live and labels the current fragment `un-UKW` (`site/src/pages/Enigma256Page.tsx:607-620`). This conflicts with the bounded C10/C24 inventory (`directives/claim-sheet.md:62-64,76-78`) and blocks claim-surface sign-off.
