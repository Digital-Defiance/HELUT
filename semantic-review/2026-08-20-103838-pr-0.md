# Nonblocking ownership for the P1030680 campaign ledger

The ledger now takes a nonblocking Darwin `lockf` lock before recovery and retains the locking handle through append and teardown. It rejects a holder that already owns the file, but initialization releases its own lock before campaign work, so the prior concurrent-writer finding remains open. The missing-file path also permits an unlocked truncation race.

Watch for: **confirmed, High** the URL-backed read closes a second descriptor and releases every `lockf` lock that process holds on the ledger; **confirmed, Medium** concurrent first-time openers can pass the existence check and a delayed `createFile` can truncate the other runner's ledger despite its advisory lock.

**Verdict**: NEEDS_CHANGES

## High-level view

Darwin `lockf` ownership is process-scoped. After taking the lock, the initializer reads with `Data(contentsOf: url)`; closing that API's descriptor releases the lock before validation, repair, evaluator work, or append. The external lock-holder test proves fail-fast acquisition only because it exits before this self-release path.

The missing-file path checks existence, calls the overwriting `createFile`, then opens and locks. Two fresh runners can both observe absence, and advisory locking does not stop a delayed creator from truncating the file. An atomic non-truncating open followed by a last-close ownership primitive removes both gaps.

## A URL read silently releases the retained-handle lock

**High severity, confirmed.** The initializer acquires `F_TLOCK` on `lockedHandle` at `Sources/HELUTToolKit/P1030680MuleinCampaign.swift:229-237`, then reads the same file by path with `Data(contentsOf: url)` at `:247`. Darwin's `lockf(3)` contract says locks are released on the first close by the locking process of any descriptor for the file; `fcntl(2)` specifically identifies library open/read/close calls as a lock-loss hazard. The URL read therefore drops the lock even though `lockedHandle` remains open.

A second campaign can then acquire ownership, accept the same prefix, and evaluate the same next plan element. Both handles may remain positioned at the same prior EOF, allowing writes to overlap or replace one another while each process advances its private completion state.

The external lock-holder test stops at `F_TLOCK` and never reaches line 247. Read from `lockedHandle` after seeking to zero, or use `flock`/an open-file-description lock whose lifetime follows the retained file description. The regression must hold runner A after ledger initialization while runner B attempts ownership; B must still fail before evaluator submission.

## First-time creation can mutate the ledger before ownership

**Medium severity, confirmed.** Lines `223-229` perform `fileExists` followed by `createFile(atPath:contents:)` before opening and locking. `createFile` overwrites an existing file; a Foundation smoke check on this host returned success for a second call and reduced a six-byte file to zero bytes.

Two runners can both observe a missing path. If runner B pauses after that stale check, runner A can create and lock the ledger before B resumes and truncates it; advisory locks do not block the truncating I/O. Open in one syscall with `O_RDWR | O_CREAT` and no truncation, wrap that descriptor in `FileHandle`, and acquire ownership before touching ledger contents. A stable sidecar lock is also viable if acquired before ledger creation.
